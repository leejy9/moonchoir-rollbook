# data-integrity-review — 데이터 관계·계산 검토

데이터 버그는 대부분 **한 화면 안이 아니라 연결부**에서 난다. 같은 사람이 두 id를 갖거나(병합), 같은 시각이 다른 시간대로 읽히거나, 보관된 것이 한쪽에서만 빠지거나, 같은 판정을 두 곳에서 다르게 하거나, 서버와 화면의 키 이름이 어긋나는 경우다.
이 스킬은 그 연결부를 빠짐없이 훑는 순서다. 코드를 고치지 않고 **발견 목록**을 만든다. 고칠 지시는 `spec-writer`로 쓴다.

## 원칙
- 기억이 아니라 **이번에 직접 연 파일·직접 실행한 쿼리**만 근거로 쓴다(파일:행, 쿼리와 결과).
- 운영 DB는 **읽기 전용**, 개인정보 값이 아니라 **개수·분포·형식만** 집계한다. 쓰기·DDL 금지.
- 발견마다 "재현 입력 → 기대 → 실제"를 적는다. 재현 못 하면 "의심"으로 표시한다.
- 독립성: 가능하면 이 검토를 구현한 사람이 아닌 새 맥락의 에이전트가 한다(`spec-audit`과 같은 이유).

## 1. 관계 지도 (ERD 표)
마이그레이션 전체를 읽어 표로 만든다.

| 테이블 | 키 | 참조(FK)와 삭제 규칙 | 생애 상태 열(보관·취소·병합·삭제) | 쓰는 함수 | 읽는 함수 |
|---|---|---|---|---|---|

- 연결 테이블(N:M)은 **연결 행의 보관**과 **양쪽 본체의 보관**을 따로 적는다.
- 추가 전용(append-only) 테이블과 그 보호 장치(트리거·RLS)를 표시한다.

## 2. 정체성·별칭
- 사람·물건이 두 개 이상의 id를 가질 수 있는지(병합, 재가입, 기기 바인딩) 확인한다.
- **사람 기준 집계마다** 별칭 집합으로 합치는지 본다(서버 함수 인자, 클라이언트 필터 모두).
- 기록을 **쓸 때** 어떤 id로 쓰는지(기기에 묶인 옛 id일 수 있음)와 **읽을 때** 합치는지 짝을 맞춘다.

## 3. 시간
열마다: 저장 타입, 쓰는 쪽 형식(시간대 표기 유무), 읽는 쪽 해석, 비교 상대.
- text 날짜·시각은 운영에서 형식 분포를 집계한다(길이, 시간대 표기 정규식).
- "오늘", "지난", "미래" 경계가 날짜만 보는지 시작 시각까지 보는지 확인한다.
- 날짜 문자열 비교와 시점(timestamp) 비교가 섞이는 곳을 표시한다.

## 4. 생애 상태별 포함 규칙
계산(지표)마다 아래 상태가 **들어가는지/빠지는지**를 표로 만들고 명세와 대조한다.
취소, 보관(본체/연결), 삭제(소프트/물리), 병합, 휴단원 등 기간 상태, 대상 외(필참 아님), 역할 차이(스태프), 아직 시작 안 한 일정, 데이터 없음(신규).

## 5. 단일 원천
같은 개념(예: 일정별 출결 상태, 공연 수, 기본값 목록)을 계산하는 곳을 `grep`으로 전부 찾는다. 둘 이상이면 서로 다른 결과가 나올 수 있는 입력을 만들어 본다. 공용 상수·함수로 모으는 지시를 낸다.

## 6. 조인·개수
- 유일 제약이 있는지(같은 사람·같은 일정 투표 1건 등), 없으면 중복 시 어느 행을 쓰는지.
- `limit`, 창 크기(최근 n개), 정렬 동점(같은 날 두 일정, 같은 order_index)에서 결과가 흔들리는지.
- 합계·평균의 분모가 명세와 같은지(0 나누기, 빈 집합).

## 7. 서버↔화면 계약
RPC·API마다 요청 인자 이름, 응답 키 이름·타입·null 여부를 서버 정의와 클라이언트 파서에서 각각 읽어 대조한다. 옛 응답(새 키 없음)도 기본값으로 읽히는지, 설정값이 문자열로 오는지(숫자·배열 변환) 확인한다.

## 8. 운영 불변식 쿼리 (읽기 전용, 개수만)
테이블마다 "0이어야 하는 개수"를 쿼리로 만든다. 예:
- 본체가 없는 연결 행(고아), 보관된 본체를 가리키는 활성 연결
- 존재하지 않는 일정·회원을 가리키는 로그·투표
- 병합된 회원 id로 계속 쌓이는 새 기록
- 분류 값(파트, 상태, 일정 구분)이 설정 목록에 없는 행 수(원문 보존이 맞는지 확인용)
- 시각 형식 분포, 미래 시각 기록, 중복 키
결과는 숫자만 보고서에 적는다.

## 9. 화면 간 일관성
같은 숫자가 두 화면 이상에 나오면(관리자 표 vs 단원 화면, 메인 카드 vs 상세 시트) 같은 입력으로 둘 다 계산해 같은지 본다.

## 10. 골든 데이터셋
1~9에서 찾은 틀리기 쉬운 경우를 모아 **가짜 데이터 1벌**을 만들고, 화면 숫자를 손으로 계산해 기대값을 적는다. 테스트 픽스처와 화면 검토(가짜 응답 주입)에 같이 쓴다.

## 11. 보고 형식
심각도 순: 치명(잘못된 숫자가 사용자에게 보임·데이터 오염) / 중요(특정 상태에서 틀림) / 낮음.
항목마다: 위치(파일:행 또는 테이블) · 재현 입력 → 기대 → 실제 · 근거 · 고칠 방향 · 기계로 막을 수 있는지(CI 가드·DB 검증 스크립트).
확인 못 한 것은 "미확인 — 이유"로 따로 적는다.
