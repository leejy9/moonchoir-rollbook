# spec-writer — 코드와 데이터를 먼저 확인하고 쓰는 명세

명세는 기억이 아니라 **이번 세션에서 직접 연 코드와 확인한 데이터**로 쓴다.
배경과 실패 사례는 `docs/agent/SPEC_WRITING.md`, 실수 기록은 `docs/agent/LESSONS.md`.

## 0. 시작 전에 읽기
- `AGENTS.md`, `docs/agent/SPEC_WRITING.md`, `docs/agent/LESSONS.md`, `.agents/rules/recurring-mistakes.md`
- 대상 명세의 결정 기록(§0)과 관련 절. 사용자 결정(V번호)과 다른 내용을 쓰지 않는다. 다르면 멈추고 사용자에게 묻는다.
- 코드를 볼 기준 브랜치를 정한다(개발 에이전트가 작업 중인 브랜치, 예: `origin/feat/v3-member-ux`). `git fetch` 후 `git show <브랜치>:<경로>` 또는 worktree로 연다. main에 없는 코드가 많다.

## 1. 바뀌는 것 한 줄 + 경로
- "무엇을, 왜" 한 줄.
- 바뀌는 데이터마다 **원천 → 저장 → 조회 → 계산 → 화면** 경로를 한 줄로 적는다. 예: `rsvp_votes(트리거) → rsvp_events → fn_get_member_activity → computePassionTemperature → 온도 카드`.

## 2. 기존 코드 계약 표 (필수, 명세 본문에 넣는다)
명세에서 가리키는 **모든** 기존 함수·컴포넌트·테이블·열·RPC·설정 키를 표로 만든다.

| 이름 | 정의 위치(파일:행) | 받는 것 / 돌려주는 것 | 빠뜨리면 생기는 일 | 대신 쓸 것 |
|---|---|---|---|---|

- 정의 위치는 `grep -n`으로 찾고 **직접 연 것만** 적는다. 표에 없는 이름은 명세에 쓰지 않는다.
- 하위 함수와 조립 함수가 같이 있으면 **조립 함수를 지목**한다(예: 일정별 출결은 `buildMemberScheduleRecords`, 하위의 `reconcileSingleMemberAttendance` 아님).
- 같은 판정이 이미 있으면 "그 함수를 재사용"이라고 이름으로 지목한다. 새로 만들게 하지 않는다.

## 3. 데이터 형식 확인
변환·비교·정렬·합산하는 열마다 실제 값의 **모양**을 확인한다.
- 스키마: `grep -n "<열>" supabase/migrations/*.sql`로 타입과 기본값.
- 값 모양: 운영 DB에서 읽기 전용으로 **형식만** 집계한다. 개인정보 값을 꺼내지 않는다.
  ```sql
  select length(timestamp) as len, timestamp ~ '(Z|[+-]\d{2}(:?\d{2})?)$' as has_tz, count(*)
  from rsvp_votes group by 1,2 order by 3 desc limit 5;
  ```
- 확인 결과를 명세에 적는다: "`rsvp_votes.timestamp`: text, `YYYY-MM-DD HH24:MI:SS`, 시간대 없음(KST)".
- 운영 DB에 쓰기·DDL을 하지 않는다. 확인 못 하면 "미확인"으로 적고 지시서에 "다르면 멈추고 보고".

## 4. 규칙 + 경계 예시
- 규칙 하나마다 **예시 2개 이상**: 정상 1, 틀리기 쉬운 경우 1(빈 값, 경계값, 시간대, 병합 회원, 오늘·미래, 보관, 스태프 등).
- 형식: `입력 → 기대 결과`. 이 예시를 지시서의 테스트 항목으로 그대로 옮긴다.
- 화면 문구는 명세에 적은 것만 쓰게 한다. 새 문구가 필요하면 명세에 정확한 문장을 적는다.

## 5. 끝에서 끝까지 손계산
- 가짜 데이터 한 건(또는 한 사람의 12회 기록)을 원천부터 화면 숫자까지 손으로 계산해 기대값을 적는다.
- 시안(디자인 아티팩트)의 숫자도 이 계산과 맞춘다. 안 맞으면 시안을 고친다.

## 6. 지시서·티켓 쓰기
`docs/plans/17_v3_implementation_guide.md`의 기존 티켓 형식을 따른다. 티켓마다:
1. 원인 또는 목적(리뷰어가 확인한 근거: 파일:행, 측정값)
2. **할 일** — 고칠 파일, 재사용할 함수(계약 표의 이름), 하지 말 것
3. **테스트** — 4번 경계 예시 그대로, "수정 전 실패 확인"
4. **확인 방법** — 테스트로 못 잡는 것(화면 폭, 실제 브라우저 동작)은 측정 방법과 보고 형식
5. 브랜치·커밋 단위·멈출 조건

## 7. 코드에 대 보기 (보내기 전)
- 지목한 파일을 다시 열어 명세 문장과 맞는지 확인한다.
- 가능하면 `spec-auditor` 서브에이전트(`.claude/agents/spec-auditor.md`)에 초안을 넘겨 **새 맥락에서** 독립 검토를 받는다. 지적을 반영하거나, 반영하지 않는 이유를 적는다.
- 이 실수를 기계로 막을 수 있으면 `scripts/ci/guards.sh`에 검사를 추가하고, 실제 위반 브랜치에 돌려 잡히는지 확인한다.

## 8. 보내기 전 점검표 (답을 명세 PR 본문에 붙인다)
- [ ] 계약 표의 모든 이름에 파일:행이 있고 이번 세션에서 열었다
- [ ] 변환하는 모든 text 날짜·숫자 열의 형식을 확인했다(또는 "미확인"으로 표시)
- [ ] 규칙마다 경계 예시가 있고 지시서 테스트에 들어갔다
- [ ] 원천 → 화면 경로를 한 건 손으로 계산했다
- [ ] 같은 판정을 두 군데서 하게 만드는 지시가 없다
- [ ] spec-auditor 검토를 받았다(또는 못 받은 이유)
- [ ] 기계로 막을 수 있는 실수는 가드를 추가했다

- 사용자가 정하지 않은 제품 결정을 명세에 넣기(질문으로 돌린다)
