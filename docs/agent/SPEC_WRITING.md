# 명세·지시서 작성 절차 (리뷰어용)

> 2026-11-23 사용자와 정리. V3-20에서 리뷰어 명세 결함 2건(출결 함수 지목, KST 문자열 시간대)이 버그로 이어진 뒤 만들었다.
> 리뷰어(Claude)는 새 세션마다 이 문서를 읽고, 명세·지시서를 쓸 때 아래 순서를 지킨다.

## 왜 틀렸나 (구조적 원인)

| 개발자들이 하는 것 | 리뷰어가 해 온 것 | 결과 |
|---|---|---|
| **계약 먼저**: 기존 함수를 지목하기 전에 정의를 열어 매개변수·반환·전제 조건을 확인한다 | 함수 이름을 기억·요약에서 꺼내 "이걸 써라"라고만 적음 | `reconcileSingleMemberAttendance`를 투표·지각 기준 없이 부르는 길을 열어 줌 |
| **데이터 사전**: 변환할 열은 타입뿐 아니라 실제 값 모양(형식, 시간대, 빈 값)을 표본으로 확인한다 | 스키마의 타입(`text`)만 보고 변환 규칙을 씀 | 시간대 없는 KST 문자열을 UTC로 읽는 규칙이 됨 |
| **경계 예시**: 규칙마다 입력→기대 출력 예시를 붙인다(그대로 테스트가 됨) | 규칙을 문장으로만 씀 | "사유결석이면 0점"처럼 틀리기 쉬운 경우가 시험되지 않음 |
| **끝에서 끝까지 추적**: 원천 행 → 저장 → 조회 → 계산 → 화면을 한 줄로 따라간다 | 화면(§5)·데이터(§7)를 따로 씀 | 투표 → 이벤트 → 온도 경로의 시간대·사유 처리 누락 |
| **설계 검토**: 코드 주인이 명세를 코드에 대 보고 서명한다 | 명세 안에서만 앞뒤가 맞는지 봄 | 코드와 어긋난 지시가 그대로 나감 |
| 긴 기억에 기대지 않는다 | 긴 대화의 요약 기억으로 코드 세부를 판단 | 세부(매개변수, 데이터 형식)가 요약에서 빠짐 |

## 쓰는 순서

1. **무엇을 바꾸는지 한 줄**과, 바뀌는 데이터의 **원천 → 화면 경로**를 먼저 적는다.
2. **기존 코드 계약 표**를 만든다. 명세에서 지목하는 함수·테이블·RPC마다:
   - 정의 위치(`파일:행`, 리뷰어가 이 세션에서 직접 연 것)
   - 매개변수와 빠뜨리면 생기는 일
   - "이 함수 대신 이것을 써라"가 있으면 그 이유
   이 표에 없는 이름은 명세에 쓰지 않는다.
3. **데이터 표본 확인**: 변환·비교·정렬하는 열은 운영 DB에서 읽기 전용으로 **형식만** 확인한다(개인정보 열은 고르지 않고, 길이·패턴·시간대 표기 여부만 집계). 확인 결과를 명세에 적는다(예: `rsvp_votes.timestamp`는 `YYYY-MM-DD HH24:MI:SS` KST, 시간대 없음).
4. **규칙마다 경계 예시 2개 이상**(정상 1, 틀리기 쉬운 경우 1). 지시서의 테스트 항목으로 그대로 옮긴다.
5. **끝에서 끝까지 한 번 따라가기**: 가짜 데이터 한 건을 원천부터 화면까지 손으로 계산해 기대값을 적는다(시안 숫자도 이 계산과 맞춘다).
6. **코드에 대 보기**: 지시서를 보내기 전에 지목한 파일을 다시 열어 명세 문장과 맞는지 확인한다. 가능하면 리뷰어가 테스트 하나를 직접 돌려 본다.
7. **모르는 것 목록**: 확인하지 못한 전제는 "미확인"으로 명세에 남기고, 개발 에이전트에게 "확인 후 다르면 멈추고 보고"를 지시한다.

## 보내기 전 점검표

- [ ] 지목한 모든 기존 함수·열에 `파일:행`이 있고, 이번 세션에서 직접 열었다
- [ ] 변환하는 모든 text 날짜·숫자 열의 실제 형식을 확인했다(시간대, 빈 값, 단위)
- [ ] 규칙마다 경계 예시가 있고, 지시서 테스트에 들어갔다
- [ ] 원천 → 화면 경로를 한 건 손으로 계산했다
- [ ] 같은 판정을 두 군데서 하게 만드는 지시가 없다(재사용할 단일 함수를 이름으로 지목)
- [ ] 이 실수를 기계로 막을 수 있으면 `scripts/ci/guards.sh`에 넣었다
