# 14. 일정 댓글 기능 개발 계획

> **작성일**: 2026-10-23
> **상태**: 기획 단계. `합의 사항`은 소유자가 대화·목업에서 직접 확인한 것입니다. `승인 필요`는 시트 구조 변경이라 소유자 승인 전에는 구현하지 않습니다(`AGENTS.md` ASK FIRST). 화면 시안은 `docs/mockups/home-comments.html`입니다.

## 1. 목적과 범위

- **목적**: 투표를 바꿀 수 없는 마감 이후나 평소에 "늦어요", "못 가요", 공지성 한마디를 카톡 게시판 댓글이 아니라 **앱의 그 일정 안에서** 남기게 해 소통이 카톡과 앱으로 갈라지지 않게 한다.
- **포함**: 단원 홈 화면의 일정별 댓글(쓰기·내 댓글 수정·내 댓글 삭제), 관리자 화면의 읽기 전용 표시.
- **제외(보류)**: 관리자의 타인 댓글 삭제·숨김(홈 화면에서 관리자 계정을 따로 구분해야 해서 큼), 푸시 알림, 말머리(`늦어요`/`못 가요`)·도착 예정 시각, 새 댓글 표시 점, 대댓글, 이미지.

## 2. 합의 사항 (소유자 확인)

1. 댓글은 **일정 하나에 붙고**, 홈의 **투표 현황 카드 맨 아래 `댓글 N ⌄` 줄**로 접고 편다. 기본은 접힘. 별도 카드·스위치·요약 칩·말머리 없음(눈에 띄지 않게).
2. 펼치면 오래된 순 목록 + 입력칸 + `등록`. 각 줄에 이름·파트 배지·내용·시각, 수정한 댓글은 `· 수정됨`.
3. **내 댓글에만** `⋯`(수정·삭제). 삭제는 한 번 더 확인.
4. 공개 범위는 단원 모두(카톡 게시판과 같음). 푸시 알림 없음.
5. 쓰기 가능 기간을 두지 않는다. 지난 일정에도 댓글을 쓸 수 있다(채팅이 아니라 댓글이고 양이 적으므로). 내 댓글 수정·삭제도 기간 제한 없음.
6. 관리자는 일정 패널에서 최근 댓글을 읽는다. 관리자 삭제는 보류.
7. 저장할 새 시트 탭 `일정댓글`을 만든다(승인, 2026-10-23). 기존 데이터 연결부와 매끄럽게 이어져야 한다.
8. **기록을 빠짐없이 남긴다.** 이상한 댓글을 쓰고 지운 사람도 시트 기록으로 찾을 수 있어야 한다. 수정·삭제 이력은 시트 로그로 충분하므로 **관리자 화면에 따로 `수정·삭제 기록 보기`는 만들지 않는다.**
9. 글자 수 제한 500자, 처음에는 최근 50개만 보이고 `더 보기`(승인).

## 3. 데이터 설계 (승인 필요)

### 3.1 구글 시트에 새 탭 `일정댓글` — 기록만 추가(append-only) 이벤트 로그
> 이 탭은 **구글 스프레드시트 파일**에 단원명부·일정캘린더 등과 나란히 생기는 저장용 탭입니다. 관리자 페이지에 추가되는 화면이 아닙니다. Apps Script가 자동으로 만들므로 사람이 따로 설정하거나 메뉴를 실행할 일은 없습니다.
출석원천로그와 같은 원칙을 따른다. 행을 덮어쓰거나 지우지 않는다.

| 열(헤더) | 의미 |
| --- | --- |
| `id` | 이 행의 고유 ID (재시도 시 같은 ID 유지 → 중복 저장 방지) |
| `scheduleId` | 일정 ID (사전투표·출석로그와 같은 키) |
| `memberId` | 작성 단원 ID (원래 ID 그대로, 통합돼도 바꾸지 않음) |
| `memberName` / `part` | 쓸 당시 이름·파트(표시용 스냅샷) |
| `action` | `CREATE` / `EDIT` / `DELETE` |
| `targetId` | EDIT·DELETE가 가리키는 원 댓글 `id` (CREATE는 비움) |
| `text` | 내용(DELETE는 비움), 최대 500자 |
| `timestamp` | 한국 시각 `YYYY-MM-DD HH:mm:ss` |
| `deviceId` | 쓴 기기(브라우저) 식별값. 이름은 기기에 저장된 정보라 사칭이 가능하므로 추적용으로 함께 남김(출석로그의 `deviceId`와 같은 값) |

**추적 가능성 (소유자 요구)**: 어떤 댓글을 쓰고 지웠는지는 이 탭만으로 알 수 있다.
- `CREATE` 행: 원문, 작성자(`memberId`·이름·파트), 시각, 기기.
- `DELETE` 행: 누가(`memberId`·이름), 언제, 어느 기기에서 지웠는지. 원문은 `CREATE` 행에 그대로 남는다.
- `EDIT` 행: 수정 후 내용·시각·기기. 수정 전 내용은 이전 행에 남는다.
- 앱은 이 탭의 기존 행을 고치거나 지우지 않는다. 다만 **시트를 사람이 직접 고치면 기록이 바뀔 수 있으므로** 시트 편집 권한은 관리자에게만 둔다(현재 시트는 소유자 단독 공유).

- **표시 규칙(투영)**: 댓글 하나의 현재 내용 = 가장 최근 `EDIT`의 `text`(없으면 `CREATE`), `DELETE`가 있으면 숨김. 수정 여부는 `EDIT` 존재로 판단. 원본은 영구 보존.
- 열은 **헤더 이름 기준**으로 읽고, 나중에 열이 추가돼도 기존 행은 기본값으로 읽는다(하위 호환).
- 대안(한 행에 `editedAt`/`deletedAt` 열을 두고 제자리 수정)은 단순하지만 append-only 불변식과 어긋나 채택하지 않는다.
- 새 탭은 Apps Script의 `ensureSheetStructure`가 첫 호출 때 만든다(기존 탭·헤더는 건드리지 않음).

## 4. 구현 단계 (`types → services → UI → verify`)

### 단계 1. 타입과 서버(Apps Script)
- `src/types/rollbook.ts`: `ScheduleCommentEvent`(원천 행), `ScheduleComment`(투영: `id`, `scheduleId`, `memberId`, `text`, `createdAt`, `editedAt?`).
- `google-apps-script.js`(+ `docs/google_apps_script.js` 동일 반영):
  - `SHEET_NAMES.COMMENTS: '일정댓글'`, `ensureSheetStructure`에 헤더 추가.
  - `doGet` 응답에 `comments` 추가(전체 반환으로 시작).
  - `doPost`에 `ADD_COMMENT` / `EDIT_COMMENT` / `DELETE_COMMENT`, 모두 기존 `LockService` 안에서 처리.
  - 서버 검사: 같은 `id` 중복 요청은 저장하지 않고 성공 응답(멱등), 글자 수 제한, 수정·삭제 시 요청한 `memberId`가 원 댓글 작성자와 같은지 확인.
- 배포 순서: **Apps Script 새 버전 → 화면 배포**(일정 공개 범위 때와 같음).

### 단계 2. 서비스(어댑터)와 파서
- `src/services/sheetsParser.ts`: `parseRemoteComments`(행 → 이벤트 정리, 누락 필드 기본값), 투영 함수(`buildScheduleComments`).
- `src/services/sheetsStorage.ts`: `STORAGE_KEYS.COMMENTS` 추가(표시용 캐시).
- `src/services/sheets.ts`(시트 통신은 여기만):
  - `fetchRemoteData`에서 `data.comments`를 파싱·캐시. 기존 화면 전환 시 새로고침(`refreshRemoteData`)에 그대로 올라탄다.
  - `addComment` / `editComment` / `deleteComment`: **시트가 저장을 확인한 뒤에만** 화면에 반영(출석과 같은 규칙), 실패하면 오류 안내. 쓸 때 만든 `id`를 재시도에서도 유지.
  - `getComments(scheduleId)`: 투영 결과를 오래된 순으로 돌려준다.
- 단원 통합 연동: 작성자 판정은 `resolveMergedMemberIds`로 통합 별칭까지 같은 사람으로 본다(내 댓글 `⋯` 표시). 표시 이름·파트는 대표 단원 현재 값을 우선, 없으면 스냅샷.
- 일정 연동: 공개 범위가 `TARGETS_ONLY`라 단원에게 숨겨진 일정은 댓글도 보이지 않고 쓸 수 없다(`getSchedulesForMember` 기준). 일정이 취소·보관돼도 댓글은 남는다.

### 단계 3. 단원 홈 화면
- 새 컴포넌트 `src/components/home/ScheduleComments.tsx`: 접힘 줄(`댓글 N ⌄`, 줄 전체 터치 48px), 목록, 입력칸+`등록`, 내 댓글 `⋯`(수정·삭제 인라인).
- 붙이는 곳: `HomeRsvpTallySection.tsx`(투표 현황 카드) 맨 아래. 일정 선택이 바뀌면 그 일정 댓글로 바뀐다.
- 규칙: 기간 제한 없음(지난 일정에도 입력 가능). 입력은 빈 내용·공백만 있으면 `등록` 비활성. 모든 터치 대상 44px 이상. 저장 실패 시 입력 내용을 지우지 않는다.

### 단계 4. 관리자 화면 (읽기 전용)
- **무엇을 보여주나**: 그 일정의 댓글을 오래된 순으로(이름·파트·내용·시각·`수정됨`), 삭제된 댓글은 숨김. 일정 목록·패널 제목 옆에 `댓글 N` 개수.
- **지금 구조(임시)**: 일정 탭 > 출결(세션) 화면의 세션 개요 카드 아래에 `댓글` 카드를 추가한다. 회차 선택창의 항목에 댓글 개수를 붙이고, 달력 하단 선택일 일정 목록의 각 일정에도 `댓글 N` 배지를 단다. 변경 범위가 작다.
- **새 일정 화면(계획서 13)**: 패널에 `현황 / 명단 / 댓글 / 수정` 탭 중 `댓글` 탭(개수 배지)으로 옮긴다. 현황 탭 아래에는 최근 3개 미리보기만 둘 수 있다.
- **관리자가 새 댓글을 알아채는 방법**: 푸시가 없으므로 개수 배지(`댓글 4`)와 달력 날짜의 표시로만 알 수 있다. "마지막으로 본 이후 새 댓글" 표시는 별도 저장이 필요해 지금은 제외.
- 관리자가 이 화면에서 직접 답글을 쓰는 기능은 없다(관리자도 단원 계정이면 홈 화면에서 쓸 수 있음).

### 단계 5. 마무리
- 계획서·`DATA_SCHEMA.md`·`ARCHITECTURE_RECOVERY.md`(데이터 저장·동기화 항목)에 새 탭과 결정을 기록.
- 실제 시트로 배포 후 점검표 실행.

## 5. 테스트와 확인 방법

- **자동(vitest)**: 투영 규칙(수정 후 내용, 삭제 숨김, 수정 후 삭제, 고아 EDIT/DELETE 무시), 누락 필드 기본값, 통합 단원 작성자 판정, 서비스의 저장 확인 후 반영·실패 시 미반영·같은 `id` 재시도 중복 방지(가짜 서버), 숨김 일정 댓글 비노출, 컴포넌트 렌더(접힘/펼침, 내 댓글만 `⋯`, 지난 일정에도 입력창 표시).
- **수동(시트 필수)**: Apps Script는 자동 테스트가 없으므로 새 탭 생성, 같은 `id` 중복 요청, 타인 댓글 수정 거부, 동시 쓰기 시 행이 섞이지 않는지를 실제 시트에서 확인한다.
- 각 단계 완료 시 `npm run typecheck`, `npm run lint`, `npm test` 통과를 확인하고 보고한다.

## 6. 위험과 한계

- **본인 확인이 기기 저장 정보 기반**: 서버가 작성자 `memberId`를 요청 값으로만 확인하므로 다른 사람 이름으로 쓰거나 남의 댓글을 고칠 수 있는 구멍이 완전히 막히지는 않는다. 투표·출석과 같은 프로토타입 한계이고 정식 운영 전 Task 76에서 함께 해결한다.
- **전체 반환 용량**: `doGet`이 댓글 전체를 매번 보낸다. 월 일정 4~8개에 댓글 수십 개 수준에서는 문제없지만, 쌓이면 응답이 커진다. 필요해지면 최근 N일치만 보내도록 줄인다.
- **반영 시간**: 저장 확인 후 반영하므로 쓴 직후 1~2초 걸리고, 다른 단원은 화면 전환·새로고침 때 본다(실시간 아님, 푸시 없음).
- **공개 댓글**: 사유(예: 건강)가 단원 모두에게 보인다. 소유자가 수용.
