### 항목 3. 물결 에너지 애니메이션
- **확인된 사실**: `src/index.css`의 `.liquid-wave-surface`가 SVG 한 장을 가로로 반복하며 `translateX(-50%)`로 움직인다. 그런데 이 SVG 경로는 시작 높이(첫 경로 y=0, 둘째 y=20)와 끝 높이(y=40, y=20)가 달라서 타일 이음새에서 파형이 끊기고, 20px 높이에 `preserveAspectRatio='none'`으로 찌그러진다. 48px 게이지에서는 이 끊김이 그대로 보인다.
- **추정**: 사용자가 말한 "그래픽이 깨져 모션처럼 안 보임"은 이음새 끊김과 찌그러짐이 원인으로 보인다. 실기기 화면은 아직 못 봤다.
- **계획**: 시작·끝 높이가 같은 사인파 타일로 교체, 겹친 두 층을 서로 다른 속도·위상으로 이동, 수면이 천천히 오르내리는 보조 모션 추가, 채움 높이가 바뀔 때 부드럽게 전환. `prefers-reduced-motion`이면 모션을 끈다. `LiquidGauge.tsx`의 props는 유지한다.
- **검증**: 0%, 12%, 50%, 99%, 100%에서 시각 확인(브라우저 캡처), 기존 테스트 통과.

### 항목 9. 모바일 관리자 매트릭스
- **확인된 사실**:
  - 왼쪽 고정 열(번호 40 + 이름 80 + 파트 65 + 상태 70 = 약 255px)과 오른쪽 고정 열(출석·지각·결석·출석률·에너지 = 약 255px)을 합치면 약 510px이다. 폰 화면(375~430px)보다 넓어서 회차 칸이 들어갈 가운데 공간이 0이 된다. 이것이 "좌우가 아예 안 보이고 드래그도 안 되는" 원인이다.
  - `public/manifest.webmanifest`에 `"orientation": "portrait"`가 고정돼 있어서 설치 앱에서는 가로 모드가 안 된다.
  - `index.html`의 viewport에 `maximum-scale=1.0, user-scalable=no`가 있어 확대가 막혀 있다.
  - 관리자 화면이 모바일일 때 `.app-shell.admin-mode[data-display-mode='MOBILE']`가 폭 480px로 제한된다.
- **계획**:
  1. 폭 640px 이하에서는 오른쪽 고정 열을 해제하고 왼쪽 고정 열을 이름 한 칸으로 줄인다(파트·상태는 이름 아래 작은 글씨로 합치기). 출석·지각·결석·출석률 요약은 이름 칸 아래나 별도 요약 줄로 옮긴다.
  2. `orientation`을 제거해 가로 모드를 허용한다(설치 앱은 재설치 후 반영).
  3. viewport의 `user-scalable=no`는 접근성상 제거를 권장한다. 단 입력창 확대 방지 목적이었다면 입력창 글자 크기를 16px 이상으로 맞춘다.
  4. 모바일 `관리자 모드` 폭 제한(480px)과 매트릭스 카드의 가로 스크롤 영역을 점검한다.
- **검증**: 375px, 430px, 가로 모드 844px에서 브라우저 캡처로 확인(가로 스크롤·고정 열·통계 가시성). 매트릭스 관련 기존 테스트(`AdminMatrixGrid.test.tsx`) 통과. 실기기 가로 모드는 소유자 확인.

### 항목 6. 카톡 인앱 QR 인식·위치 인증 실패
- **확인된 사실**:
  - QR 내용이 URL이 아니라 JSON 텍스트(`src/utils/qr.ts`)라서 아이폰 기본 카메라로 찍어도 앱이 열리지 않는다. 앱 안의 카메라(`getUserMedia`)로만 인식된다.
  - 카메라 실패는 한 문구("카메라를 실행할 수 없습니다")로 뭉뚱그려진다. 위치(GPS) 실패도 거부·시간 초과·미지원을 구분하지 않고 한 문구로 처리한다(`QRScannerModal.tsx`). 위치 요청은 `enableHighAccuracy: true`, `timeout: 8000`이고 재시도·저정밀 대체가 없다.
  - 웹 조사: iOS의 인앱 브라우저(WKWebView)는 카메라·위치 권한을 앱이 따로 허용해야 하고, 앱·웹 사이의 권한 불일치로 문제가 생긴 사례가 있다. 다만 **카카오톡 인앱 브라우저가 카메라/위치를 막는지는 이번 조사에서 확인하지 못했다.**
- **추정**: 아이폰에서만 두드러지는 것은 WKWebView 권한 처리 때문일 가능성이 높다. 실기기 확인이 필요하다.
- **계획(안전하게 할 수 있는 개선)**:
  1. 오류를 원인별로 구분: 카메라 권한 거부 / 카메라 미지원(`navigator.mediaDevices` 없음) / 위치 권한 거부 / 위치 측정 시간 초과 / 위치 신호 없음. 각각 사용자가 할 행동을 안내한다.
  2. 위치는 고정밀 측정 실패 시 한 번 더 저정밀로 재시도하고, 측정 정확도(±m)를 결과에 보여준다. 거리 판정 기준(반경)은 바꾸지 않는다.
  3. 카카오톡 인앱 브라우저로 감지되면 QR 화면 상단에 `기본 브라우저로 열기` 안내를 보여준다(`pwaInstall.ts`의 기존 `buildKakaoExternalBrowserUrl` 재사용).
  4. 카메라가 안 될 때 PIN 출석으로 넘어가도록 안내한다.
- **검증**: 에러 분기 단위 테스트, 모의 `geolocation`/`mediaDevices`로 컴포넌트 테스트, 모든 Green Bar. 실기기(아이폰 카톡 인앱/Safari, 안드로이드 카톡 인앱/Chrome) 결과는 소유자 확인 필요.
- **별도 검토(큰 기능)**: QR을 URL로 바꿔 아이폰 기본 카메라로 앱을 열고 자동으로 출석 화면까지 연결하는 방식. 이미 붙인 상설 QR을 다시 인쇄해야 하고 URL 처리·인증 흐름이 새로 필요하므로 별도 결정 대상이다.

### 결정 1. 항목 7 — 출석했는데 `미응답`으로 남는 문제
- **확인된 사실**: `HomeView.tsx`에서 `unvotedMembers`는 대상 단원 중 투표 기록이 없는 사람이다. 출석 로그는 보지 않는다. `RSVP`는 각 단원의 현재 응답만 보관하며(합의 사항), 투표 마감은 시작 1시간 전이다.
- **권장안 (표시만 바꾸기)**: 출석 기록이 있는 사람은 `미응답`에서 빼고, `참석` 쪽에 `현장 출석`으로 따로 합산해 보여준다. 예: `참석 12 (투표 10 · 현장 2)`.
- **하지 말아야 할 방식**: 출석 시 시트의 투표(`RSVP`)를 `참석`으로 자동 변경하는 것. 아래 단점이 크다.
- **장점(표시 방식)**: 데이터를 건드리지 않아 `append-only`·투표 정책과 충돌하지 않는다. 관리자 매트릭스의 `참석투표` 표기(투표 후 불참)와 구분이 유지된다. 출석을 취소(초기화)하면 자동으로 원래대로 돌아온다.
- **단점·주의**:
  - 투표율의 의미가 바뀐다(사전 예측용 지표 + 실제 출석 혼합). 그래서 `투표`와 `현장`을 분리 표기한다.
  - 투표 `불참`인데 출석한 사람도 처리 기준이 필요하다. 권장: 실제 출석이 우선이고 `현장 출석`으로 표기한다.
  - `RSVP`를 실제로 바꾸는 방식은 마감 시각 규칙, 운영자 예외, 되돌리기, 시트 쓰기 실패 시 불일치를 모두 새로 처리해야 해서 위험이 크다.
- **질문**: 표시만 바꾸는 권장안으로 진행해도 되는가? `불참` 투표 후 출석한 사람을 `현장 출석`으로 보여도 되는가?

### 결정 2. 항목 4 — 출석·지각 시각 지정
- **확인된 사실(중요)**: 관리자 수동 출석은 `createManualLogMeta()`가 **지금 시각**을 로그 시각으로 저장한다(`useAttendanceAdmin.ts`). 지각 판정은 로그 시각이 시작 시각 + 유예 분(기본 10분)을 넘거나 관리자 메모에 `지각`이라는 글자가 있으면 지각으로 처리한다(`attendanceStats.ts`). 그래서 연습이 끝난 뒤에 수동 출석을 입력하면 실제로 일찍 왔어도 지각으로 계산될 수 있다. 메모에 `지각하지 않음` 같은 문구를 써도 지각으로 잡히는 문제도 있다.
- **선택지**:
  - A. **도착 시각 입력 (권장)**: 수동 출석 창에 `도착 시각`(기존 `RoundTimePicker` 재사용)을 넣고, 그 시각을 로그의 `timestamp`로 기록한다. 지각은 기존 유예 분 규칙으로 판정. 스키마 변경 없음. 단점: 실제 입력한 시각이 로그에서 사라지고(입력 시점이 아니라 도착 시각이 기록됨) 입력 사실은 메모로만 남는다.
  - B. **상태 직접 선택**: `출석` / `지각` 버튼. 판정 기준이 시각이 아니라 관리자 선택이 된다. 단점: 지각 판정이 두 방식(시각·선택)으로 갈린다.
  - C. 입력 시점 시각을 별도 열(`recordedAt`)로 보존: 가장 정확하지만 시트 열 추가라 `ASK FIRST`이고, 복구 기록의 "시도 시각과 시트 확정 시각 보존" 원칙과도 연결되므로 별도 설계가 필요하다.
- **권장**: A에 더해 `지각`이라는 글자로 판정하는 방식은 유지하되(기존 데이터 호환) 새 입력에서는 쓰지 않는다. 입력 시점은 메모에 자동으로 덧붙인다(`입력 2026-10-23 14:02`).
- **질문**: A로 가도 되는가? 지각 유예 분(기본 10분)은 지금 설정(`AdminSettingsTab`)을 그대로 쓰는가? 출석 입력 전에 "이미 출석 기록이 있는 사람"의 시각 수정도 허용할 것인가(추가 로그로 처리됨)?

### 결정 3. 항목 8 — 일정 공개 대상 제한
- **확인된 사실**: 대상자 지정은 이미 있다(`ALL`, `ALL_WITH_GUESTS`, `PARTS`, `CUSTOM_MEMBERS`). 합의된 규칙은 "모든 일정은 보이고, 대상이 아닌 단원에게는 `자율 참여 연습`으로 보인다"이다(복구 기록 2026-10-20 합의 4). 새 요구는 이것과 반대로 일부 일정을 비대상자에게 **아예 숨기는 것**이다.
- **필요한 변경**: 일정에 `공개 범위`(예: 전체 공개 / 대상자만) 속성을 추가해야 한다 → `일정` 시트에 열 추가 = **스키마 변경이므로 사전 승인 필요**(`AGENTS.md ASK FIRST`). 기존 행은 비어 있으면 `전체 공개`로 해석한다(하위 호환).
- **주의점**:
  - 숨김은 **화면에서만** 숨긴다. 앱이 시트 전체를 받아서 브라우저가 거르는 구조라, 기술적으로는 숨긴 일정도 데이터에는 들어 있다. 보안·비밀 유지가 목적이면 Task 76(서버가 역할별 데이터를 돌려주기)이 먼저 필요하다. 이번 목적은 "굳이 안 보여줘도 되는 사람에게 노출하지 않기"이므로 화면 숨김으로 충분한지 확인이 필요하다.
  - 숨긴 일정의 처리 규칙이 필요하다: 비대상자의 자율 출석 허용 여부, 상설 QR의 자동 일정 매칭(`findActiveScheduleForMasterQR`)에서 제외 여부, 캘린더·홈 목록·관리자 목록(관리자는 항상 보임), 통계 모수(이미 대상자만 모수).
  - 요청한 `필참은 아니지만 참석 가능해요`는 `대상자만 보임` + `자율 참여 허용`의 조합으로 표현할 수 있다.
  - 일정 카드(`ProgramCard`)의 대상자 상속 규칙(합의 3)과 같은 방식으로 카드 단위 기본값을 상속할지 정해야 한다.
- **질문**: 화면 숨김만으로 충분한가? `일정` 시트에 열을 추가해도 되는가? 숨긴 일정에서 비대상자의 자율 출석을 허용할 것인가?

### 항목 5. 바인딩(이름+번호 인증) 반복
- **확인된 사실**: 인증 정보는 브라우저 `localStorage`(`moonchoir_bound_device_v1`)에 저장되고, 같은 브라우저에서는 닫았다 열어도 유지된다. 코드가 스스로 지우는 경우는 두 가지다: 로그아웃, 그리고 시트에서 새로 받은 명부에 그 단원 ID가 없을 때(`App.tsx`). 저장소 접근이 막히면 메모리 저장으로 바뀌어 창을 닫으면 사라진다(`auth.ts`).
- **가능한 원인(미확인, 증상별로 확인 필요)**:
  1. 카카오톡 인앱 브라우저·사파리·크롬·설치 앱은 서로 저장소가 분리된다. 링크를 열 때마다 다른 브라우저가 열리면 매번 인증하게 된다. 설치 앱이 사파리와 저장소를 공유하지 않는 것도 같은 문제다.
  2. 사파리 등은 일정 기간 방문하지 않으면 저장소를 지울 수 있다(일반 지식이며 이번 조사로 확인하지 않음).
  3. 명부 정리·병합으로 단원 ID가 바뀌면 자동 로그아웃된다.
  4. 비공개(시크릿) 모드, 방문 기록 삭제.
- **다음 행동**: 반복 인증을 겪은 단원 2~3명에게 (가) 카톡 링크로 열었는지 사파리/크롬으로 직접 열었는지, (나) 아이폰/안드로이드, (다) 설치 앱 사용 여부, (라) 얼마나 자주 묻는지를 확인한다. 그 결과를 보고 `navigator.storage.persist()` 요청, 자동 로그아웃 시 안내 문구 추가, 인앱→기본 브라우저 유도 강화 중 필요한 것을 고른다.
- 1인 1기기 잠금 복원(Task 85)과 같은 흐름이라 함께 정리한다.

### 항목 2. 홈 화면 바로가기가 안 뜨는 경우 (웹 조사)
- **iOS**
  - 홈 화면 추가는 기본적으로 **사파리의 공유 메뉴**에서만 된다. 크롬 등 다른 브라우저는 iOS 16.4부터 지원이 가능하지만 브라우저가 따로 구현해야 하고, 지금도 지원하는지 이번 조사에서 확인하지 못했다.
  - **인앱 브라우저(카카오톡 등)와 QR 미리보기 화면**에는 `홈 화면에 추가`가 없다. 링크를 길게 눌러 사파리로 열어야 한다.
  - iOS 26부터는 홈 화면에 추가한 사이트가 기본적으로 웹 앱으로 열리고, 추가 창의 `웹 앱으로 열기` 스위치로 끌 수 있다. iOS 26 초기 베타에는 홈 화면 추가가 안 되는 버그 보고가 있었다(최신 버전에서는 고쳐진 것으로 보인다는 답변).
  - 사파리는 설치 안내 팝업을 띄우지 않는다. 사용자가 직접 해야 한다.
- **안드로이드**
  - 크롬은 매니페스트·서비스 워커·HTTPS·192/512 아이콘 조건을 만족하면 앱처럼 설치(WebAPK)하고, 조건이 부족하면 단순 바로가기만 만든다. 우리 앱은 이 조건을 갖췄다(매니페스트, 서비스 워커, 아이콘 192/512).
  - **삼성 인터넷**: Android 14 이상에서 설치가 `오래된 안드로이드용 앱` 경고로 막히는 사례가 보고돼 있고, 같은 기기에서 크롬은 정상이다. 매니페스트의 `share_target`(POST)이 있으면 조용히 실패하는 사례도 있는데 **우리 매니페스트에는 `share_target`이 없다**.
  - 아이콘을 삭제하고 앱은 남은 상태에서 다시 설치하면 이미 설치됐다고 인식되는 사례가 있다. 앱을 지운 뒤 다시 설치해야 한다.
  - 런처 설정이나 제조사 정책으로 홈 화면에 아이콘이 자동으로 안 놓이고 앱 목록에만 생기는 경우는 일반 지식이며 이번 조사로 확인하지 못했다.
- **우리 앱에서 개선할 수 있는 것**
  - `InstallAppCard`에 삼성 인터넷 감지 시 `크롬으로 열기` 안내 추가.
  - iOS 안내 문구를 `사파리에서 열기 → 공유 → 홈 화면에 추가`로 구체화하고, iOS 26의 `웹 앱으로 열기` 스위치를 켜 두라고 안내.
  - `maskable` 아이콘이 일반 아이콘과 같은 이미지(여백 없음)라서 안드로이드 원형 마스크에서 로고가 잘릴 수 있다. 여백이 있는 별도 아이콘을 준비한다(기존 `확인·정리 대기`의 아이콘 교체와 함께).
- **필요한 정보**: 안 뜬 단원들의 기기·OS 버전·브라우저(예: 갤럭시 + 삼성 인터넷, 아이폰 + 카톡 인앱). 이번 조사로는 OS 버전별 정확한 조건을 확정하지 못했다.

### 항목 10. 시트 접근 제어
- **확인된 사실**:
  - 구글 드라이브 권한 조회 결과, 이 스프레드시트의 접근 권한은 소유자 한 명뿐이다. 링크 공개가 아니다. 관리자 화면의 `시트 ↗` 버튼이 바로 열리는 것은 소유자가 같은 브라우저에서 구글에 로그인돼 있기 때문이고, 다른 사람이 누르면 구글의 접근 요청 화면이 나온다.
  - 시트 주소(문서 ID)는 코드에 있고 저장소가 **공개(PUBLIC)** 라서 누구나 볼 수 있다. 다만 주소만으로는 시트가 열리지 않는다.
  - **더 큰 노출은 시트가 아니라 앱 서버다.** Apps Script 웹 앱 주소가 공개 저장소(`src/services/mockData.ts`)와 배포된 사이트에 들어 있고, 접근 권한이 `링크가 있는 모든 사용자`다. 서버가 단원 명부(전체 전화번호), 출석 기록, 관리자 PIN까지 돌려주고 서버에 역할 검사가 없다. 시트가 비공개여도 이 주소만 알면 같은 데이터에 접근하거나 수정할 수 있다. 소유자가 프로토타입 범위에서 수용한 위험이고(Task 76) 정식 운영 전 필수 항목이다.
  - 이번 테스트 배포에는 실제 단원 이름·번호가 들어갔을 가능성이 있어 위험의 무게가 달라졌다(이는 추정이며 시트 내용은 열람하지 않았다).
- **논의 필요**:
  - `시트 ↗` 버튼을 관리자 로그인 뒤에만 보이게 하는 것은 이미 그렇다. 버튼을 숨기거나 ID를 코드에서 빼는 것은 보안 효과가 거의 없다.
  - 원하시는 "구글 로그인한 허락된 계정만"은 시트 자체에는 이미 적용돼 있다. 앱 쪽에 적용하려면 관리자 화면에 구글 로그인(Google Identity Services)을 넣고 Apps Script가 로그인 토큰과 허용 계정 목록(이메일)을 검증하는 방식이 가능하다. 이는 관리자 PIN을 대체하는 설계이므로 별도 승인 후 Task 76과 함께 진행한다.
  - 단계 제안: (1) 서버 응답에서 `adminPin`·전체 전화번호부터 제거, (2) 관리자 쓰기 요청에 구글 토큰 검증, (3) 단원 요청에 역할별 최소 데이터.
- **질문**: 실제 단원 정보가 들어간 상태이니 Task 76을 이번 개발 순서에서 앞당길 것인가?

### 항목 1. 구글 캘린더 연동 (검토만)
